### 2.3 分かったこと

- Play をまたぐと、結果は最初から 1 ビットも同じ（det2・det3・det5 が完全一致）
- **同じ Play の中で続けて回すときだけ、PhysX の内部に前の候補の履歴が残る**
- 指を戻していなかった（step 0 からズレていた）のは、①で解決
  - wrist-up へリセットした直後、指が約 3.4° ずれていた
- step 219 からのズレは、指先が机やターゲットに近づいて、新しい「接触の組」ができるあたり
  - 接触の組を作る順番などが履歴で変わる、と推測。ただし特定まではしていない
- ロボットの自己衝突（指のリンクどうしなど）を無視すると、ズレがターゲットに触れた後まで遅れた。それでも消えはしなかった
- 当たり判定を外してすぐ付け直すと、同じフレームでは何も起きない（PhysX に反映されない）

### 2.4 詰まったところ

1. **Enhanced Determinism が効かない**
   - 設定だけでは物理ワールドに反映されないかもしれないと考えて、Taro に Unity を再起動してもらった
   - 再起動しても結果が 1 ビットも変わらなかった。履歴の問題は、この設定では消えない
2. **ロボットを別のシーンへ移すと腕が暴れる**
   - 上腕の関節が −9.7 rad になり（範囲は ±180°）、追従誤差が 1 m 近くになった
   - 原因：ArticulationBody は、移したときの Transform から作り直される。そのとき関節角の 0 が「今の姿勢」にずれる
   - 対策 1：移す前に、物理で全関節を 0 へ動かす → 動いたけど、1e-6 m ずつズレて step 0 から結果が違った
   - 対策 2（採用）：**`Awake` で覚えておいた「シーンに置いたときの Transform」を直接書き戻してから移す** → 完全に一致
3. **計画失敗のエラーで Play が止まる**
   - wrist-up の計画が失敗したとき、`LogError` で Error Pause が働いて Play が一時停止した（`isPaused = true`、`Time.time` が 3.4 s のまま）
   - P5 の項目を先にやって `LogWarning` にした
4. **シーンの「読み込み直し」が効いていなかった**
   - `OpenScene` で今開いているシーンを開いても、メモリ上の変更が捨てられない
   - さらに、テスト用の `outputRoot` がシーンファイルに保存されてしまったことが 1 回あった
   - `git checkout` でシーンファイルを戻して解決
   - 以後は **`NewScene`（空）→ `OpenScene`** の順で読み込み直す
5. **VM から `git diff --stat` を打つと 180 ファイル変更と出た**（改行・権限の差）
   - 書き込みはしていないので無害。以後も git は Unity から起動する

## 3. P4-B②：押し方（1 回目）と、倒れた判定のバグ

### 3.1 押し方の比較（ブレの調査と並行、P4-B①の途中）

| 押し方 | 箱の動き | 同じ候補の差 | フォルダ |

- Taro の判断：「押し方を安定させる（Recommended）」「まず物理シーンの作り直しを試して、ダメなら Play し直し」

### 3.2 詰まったところ：押し始めの位置が 10 cm ずれた

- 指を閉じると、押し始めまでの距離が変わる。そこで、グリッパーの当たり判定の形から計算する `contactFromGeometry` を入れた
- 最初は前に出ている距離が 106 mm と出て、押し始めが遠すぎた
- 原因：運動学（TCP の位置）とグリッパーの頂点を `Start()` で作っていた
  - そのときは、`RobotInitialPose` が指を閉じた結果がまだ Transform に反映されていない（物理が 1 回も回っていない）
- 対策：`Run()` の最初（30 フレーム後）に作るように移した
- `robotiq_arg2f_base_link` という名前の Transform が複数あって、デバッグでは違う方を拾っていた
  - コードは「ArticulationBody を持つもの」で探すようにした

### 3.3 大きな発見：横倒しを見逃していた

- 回転を調べたら、**P4-A のパイロットの全候補で、立方体が横倒し（上向きの軸が 90° 傾いた）になっていた**
  - 立方体は横倒しになっても中心の高さが変わらない。だから、高さだけの「倒れた」判定（2 cm 下がったら）では見逃していた
  - goal True の 4 件も、実際は「倒れた箱の中心がゴールに入った」だけ
- 「閉じた指 ＋ 90° 回す」でも、6 方向中 2 方向（−90°・−45°）で倒れた
  - ナックル（指の上の方の部品）が前に出ていて、箱の上の方を押していたため
  - 押す高さを変えたときの前に出る距離：TCP の高さ 0〜20 mm で 7 mm、30〜40 mm で 19〜20 mm
- 対策：指先を押す方向へ 30° 傾けて、指先が先に当たるようにした → 6 方向とも立ったまま（`p4b_v14`）
- 傾けると、wrist-up の計画が transfer の途中で失敗した（手首の関節が ±180° に引っかかる）
  - `CandidateSpec.gripperYawFlip`（接近方向まわりに 180° 回す）を追加した
  - 閉じた指は左右対称なので、押し方は同じ
  - mp0：TCP の差 0.071 mm、前腕の差 22.5 cm

### 4.2 作ったもの（`Assets/Scripts/SceneGenerator.cs`、新規）

- `EpisodeRecorder.autoScene.enabled` ＋ `seed` で、Play 1 回で全部決まる。中身は各 scene の `scene_generation.json` に書く
- **ターゲット**：x −0.15〜0.15、z 0.22〜0.42、向き 0〜90°。箱の 8 つの角が画面の端から 5% 以上内側に写ること
- **ゴール**：ターゲットから 6〜12 cm、押せる方向（計画できる方向）に置く
- **matched pair**：wrist-down と wrist-up（初期値 `[−64, −122, 117, 95, 90, 116]°`）。どちらかが失敗したら `gripperYawFlip` で計画し直す
- **単独候補**：ゴール方向（± 10°、距離 = ゴールまで ＋ 1.5 cm ± 3 cm）とランダム方向
- **外す条件**（`reject_reasons` に記録）：
  - `near_base`：押し始めが土台から 25 cm 未満
  - `target_end_off_table`：押した後のターゲットが机の端から 6 cm 以内
  - `ik_failed`：IK が解けない
  - `joint_step`：1 step で関節が 2° より大きく動く
- **円柱の置き場所**：matched pair の 2 本の軌道で、腕と手の当たり判定の頂点を動かして探す

| 条件 | 値 |
|---|---|
| 片方の腕の重なり | 3〜10 mm |
| もう片方の腕との隙間 | 3 cm 以上 |
| 手との隙間 | 2 本とも 2.5 cm 以上 |
| ターゲットの通り道との隙間 | 3 cm 以上 |
| ゴールとの距離 | 6 cm 以上 |
| その他 | 画面に写る |

- ターゲットは向きのある箱として計画する（`TrajectoryPlanner.Support`）。前は AABB だったので、回した箱だと押し始めがずれた

### 4.3 詰まったところ

1. **斜めの面を押すと、箱が横へそれる**
   - 最初はゴールの方向を全方向からランダムに選んでいた。ターゲットを回してあると、押す方向から約 40° それてゴールに入らなかった
   - → ゴールの方向を「ターゲットの面の法線 ± 10°」にした
2. **傾き 30° だと倒れる**
   - ターゲットの向きを変えると、ゴール方向の 6 本のうち 4 本が倒れた
   - 理由：指先を前に傾けると、押す力に上向きの成分が出る（接触面の法線が前上向き）
   - → 15° にした（倒れた 0）
3. **円柱の近くを通るだけで Task B がずれる**（最大 3 mm）
   - 円柱から 2 cm 以内を腕が通ると、PhysX が円柱をロボットと同じ計算のまとまりに入れる
   - → contactOffset をロボット 2 mm・円柱 1 mm に小さくした → 0.000 mm
4. **「衝突」に触れていない接近が混ざっていた**
   - PhysX は contactOffset（既定 1 cm ずつ）以内に近づくと、隙間 > 0 でも接触として報告する
   - → `contacts.csv` に `min_separation` を追加。隙間 1 mm 以下だけを数える（`contactTouchTolerance`）
   - 検証も同じ規則にした。**P3 までの衝突ラベルにも、近づいただけのものが混ざっていた可能性がある**
5. **円柱の置き場所が見つからない**
   - 1 cm の格子で近似すると、誤差が最大 7 mm 出た。格子で「重なり 6 mm」と出た場所が、実際は 3〜11 mm 離れていた
   - → 格子で候補を集めて、良さそうな所だけ「頂点とカプセルの距離」で正確に測る。さらに、重なりが 6.5 mm になるように中心をずらして測り直す
6. **生成中は Unity が応答しない**
   - 生成は Unity のメインスレッドで回るので、MCP が 60 秒で応答なしになる。待てば終わる
7. **`executed_meta.json` が壊れていた**

## 5. P4-B④：本番の入力仕様（commit `acd741d`）

## 12. 今回の教訓（MCP 作業のルール、追加分）

| 教訓 | ルール |
|---|---|
| `OpenScene` で今開いているシーンを開いても、メモリ上の変更が捨てられない | `NewScene`（空）→ `OpenScene` で読み込み直す。保存したシーンに `outputRoot` などが入っていないか、commit 前に確認する |
| 計画失敗の LogError で Error Pause が働き、Play が止まる | 続けられる失敗は LogWarning。Play が進まないときは `isPaused` を確認する |
| 物理の設定（ソルバー・broadphase など）は、候補ごとに作る物理シーンに反映される | 設定を変えたら、再起動しなくても次の Play で試せる |
| ArticulationBody はシーンを移ると、今の Transform から作り直される | 移す前に、リンクの Transform をシーンに置いた値へ戻す |
| PhysX は contactOffset 以内に近づくと、触れていなくても接触を報告する | ラベルは `min_separation` ≤ 1 mm だけを数える |
| 立方体は横倒しでも中心の高さが変わらない | 倒れた判定は傾きでも見る |
| Unity のメインスレッドで重い処理（生成・Python の同期実行）をすると、MCP が 60 秒で応答なし | 待つか、別プロセスで起動してログをファイルに書かせる |
| Perception の depth の EXR は R チャンネル | cv2 では index 2 |
| 共有フォルダ越しの VM では、ファイル一覧が遅れて見えることがある | 移動した直後は、もう一度確認する |
| VM から読み込み速度を測ると遅く出る | Windows の Python で測る |
